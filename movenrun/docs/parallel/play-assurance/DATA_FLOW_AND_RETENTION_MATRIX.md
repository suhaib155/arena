## 2. Local-device summary (what a rooted-device or forensic reader could see)
- Unencrypted AsyncStorage can hold precise route points of up to 3 unsent sessions for up to 7 days after session end, only when a Save failed. Auth tokens are in Keystore-backed SecureStore, not AsyncStorage.
- Cloud backup and device-transfer are excluded: allowBackup=false and a data-extraction rules plugin (M/app.json:22; M/plugins/withNoBackupTransfer.js:19-39). Merged manifest NOT RUN.
- Gap to disclose: expiry is enforced when the queue is accessed. If the app is not opened, the file stays until the app next runs or is uninstalled (M/src/services/verificationQueue.ts:1-3).

### Partial-failure visibility
- API reports `signInRecord:"pending"` when the provider is unreachable (B/identity/http/router.ts:372).
- Live website ignores it: success whenever the HTTP response is ok (W js account-deletion-page.js:37 per WEBSITE_FACTS Part 2). The page copy discloses retry in general but never tells the person their own case is pending.
- Mobile client type is `{deleted: boolean}` and discards signInRecord (M/src/services/identityApi.ts:471-476). Same blind spot.
- LOCAL TEST CONFIRMED (research/play-assurance/tests/authAssurance.test.ts:123-149): a failed provider deletion is queued and due for retry (control); if the same Google account signs in again while the deletion is pending, a new MovenRun account maps to the same subject, `removeProviderUsers` correctly keeps the mapped user, but the queue row is neither removed nor marked attempted, so it stays due on every run and holds a slot in the 50-row batch. Class: LOCAL TEST CONFIRMED (Track C test as reported; not re-run by this writer).
- Consequence to tell the owner: wording "deleted straight after" is true on the normal path only. A re-sign-in during pending state makes a new account whose provider record is the same record.
