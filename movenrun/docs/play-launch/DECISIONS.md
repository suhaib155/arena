# Decisions (Play v1)

Each decision records what was chosen, why, and what would reverse it.

| ID | Decision | Why | Reversal |
|---|---|---|---|
| D-01 | Play v1 is **Path A, Movement Game v1**: walk/run sessions, missions, XP, streaks, badges, personal ground preview, share image, optional account (Google or wallet sign-in, D-16). No tokens, wallet features beyond sign-in, NFTs, Deeds, clubs or multiplayer competition | Owner mandate. Those surfaces depend on economy, density and policy work that is not launch-ready, and Play financial/blockchain declarations would follow from them | A later release flips a flag in `releaseScope.ts` after its own review |
| D-02 | Deferred features are **hidden, not deleted**: `mobile/src/lib/releaseScope.ts` switches them off, the root layout guard sends deferred routes home, and `releaseScope.test.ts` fails if any entry point stays reachable | Repository working agreement: preserved assets are not deleted | Set a feature to `true` |
| D-03 | Android id stays `io.movenrun.app`; version code is managed remotely by EAS (`appVersionSource: remote`, `autoIncrement` on production) | A package name cannot change after first upload; remote version codes avoid collisions between CI and local builds | None |
| D-04 | Release manifest declares only fine and coarse foreground location; background location, foreground service, overlay, storage, media and audio are removed with `blockedPermissions` | Avoids the background location and foreground service declarations; matches the foreground-only product | A feature that genuinely needs one, with its Play declaration |
| D-05 | Account deletion is a **hard delete** of every row tied to the account in one transaction, leaving one anonymous `account_deleted` audit row. Available in app and on the web (`website/account-deletion/`) | Play account deletion policy; nothing in v1 needs retained personal data | A legal hold requirement would add a documented retention exception |
| D-06 | **Superseded by D-21 (2026-10-13).** Was: reviewer access through a server-side **review email + fixed six-digit code** (`IDENTITY_REVIEW_EMAIL`, `IDENTITY_REVIEW_CODE`), not a bypass. Guessable codes are refused; all OTP limits still apply; no email is sent for that one address | Reviewers cannot receive codes at our test inbox; the code never sits in the repo | Unset both variables after review if desired |
| D-07 | After reinstall, the account shows its **verified sessions (count and distance) from the server**; local XP, streaks and quests are device-only in v1 and do not restore | Restoring game progress server-side is a larger feature; v1 copy never claims it does | A progress sync feature |
| D-08 | The production AAB is built only by **EAS in GitHub Actions** (`eas-production-aab.yml`), after lint, tests, Hermes export, prebuild and a manifest permission check, in the `play-release` environment | No Android SDK download is possible in this workspace; keeps signing in EAS and the build reproducible from a commit | None |
| D-09 | Signing: **Play App Signing** with an EAS-managed upload key | Google holds the app signing key; a lost upload key can be reset | None |
| D-10 | **Superseded by D-23 (2026-10-13).** Was: production hosting not chosen; `render.yaml` had paid plans. A free Postgres (for example the owner's Supabase project, used as plain Postgres through `DATABASE_URL`) plus a Node host is the alternative | The mandate forbids spending without approval | Owner choice |
| D-11 | An unused third-party SDK dependency was removed from the backend (no imports) | Smaller attack surface | None |
| D-12 | Store listing describes only what v1 does; "ground" is called a personal preview kept on the device, never ownership or earnings | Play deceptive behaviour and financial policies | None |
| D-14 | Every table has **row level security on with no policies** (migration 0006); new tables must do the same, enforced by `runtime.test.ts` | A managed Postgres (Supabase) publishes `public` through a REST API; this keeps that API empty even if it is left on. The server connects as the table owner and is unaffected | None |
| D-15 | **Default staging host while X-03 is open: Supabase Free (PostgreSQL only, session pooler, verified TLS) + Render Free web service**, migrations in the start command | Costs nothing; the owner already has the Supabase project. Free instances sleep, so production should move to an always-on plan with approval | Owner picks another host |
| D-13 | No pull request is merged and nothing is published by this work; the owner merges and presses Publish | Mandate section A | None |
| D-16 | **Owner decision 2026-10-13: sign-in is "Continue with Google" and "Continue with Wallet" through Supabase Auth** in the existing Free project `movenrun` (ref `tavxmwuwkeynbnzfwove`, us-east-1). Guest play stays. Email codes and Resend are no longer v1 requirements: the email routes are not mounted unless a delivery key is set, and the app no longer shows the email form (code kept, not deleted). Express and PostgreSQL keep all game data | Owner decision; no email provider to run | Owner |
| D-17 | MovenRun accounts are keyed to the **Supabase user id** (identity provider `supabase`). Nothing is ever matched by email or wallet address. **Google and wallet sign-ins are separate accounts; linking is not offered in v1.** Doing it safely needs Supabase manual identity linking plus re-authentication of both methods and a merge rule for two existing accounts, which cannot be proven on a phone by the device gate. **Accepted by the owner on 2026-10-13 ("accept separate accounts", X-20)** | A wrong link hands one person's progress to another | Owner accepts linking as a v1.1 feature |
| D-18 | Wallet sign-in accepts **plain EOA wallets only** (contract wallets / EIP-1271 refused). The **server** writes the EIP-4361 message (domain `movenrun.xyz`, URI `https://movenrun.xyz/sign-in/`, chain id 8453 for the message only, single-use nonce, 5-minute expiry), checks nonce, exact message and signature itself, then passes it to Supabase's Web3 grant. No transaction, no gas, no custody, no balance read | Replay and phishing resistance without trusting the client; nothing on chain | A verifier for EIP-1271 |
| D-19 | **Wallet sign-in in the Android app goes through the wallet's own browser**: the app opens `movenrun.xyz/sign-in/` in MetaMask, Coinbase Wallet or Trust Wallet with a PKCE challenge; the page gets a 12-character one-time code that only this phone's verifier can spend, returned by `movenrun://auth/wallet` or typed in. No WalletConnect SDK, no project id, no new native module | Works with no extra provider account and no native wallet SDK on RN 0.81; the code is useless without the verifier. Risk: a wallet browser may not open the app link (typed code is the fallback). **Must be proven on a phone by 24 Oct, otherwise flag `WALLET_LOGIN_BLOCKED` and ask the owner for Google-only or a deferral** | Owner provides a WalletConnect project id and a device-tested SDK replaces it |
| D-20 | **1,000 registered accounts, counted across Google and wallet together.** The API admits a new account only under a Postgres advisory lock against `account_capacity.max_accounts`; the Supabase before-user-created hook (`public.movenrun_before_user_created`) stops new provider users at the same count; a provider user refused at the cap, left by an erased account or by an uncollected wallet code is deleted at Supabase (retried until it succeeds). Existing players always sign in. Capacity alerts at 80, 90, 95 and 100 % (audit row + log line with counts only) | Free-tier limits and a controlled first release | Owner changes `max_accounts` (one SQL row) |
| D-21 | **Reviewer access: guest play, or "Continue with Google" with the reviewer's own Google account.** No email code, no seed phrase, no test wallet, no ETH | Google reviewers have Google accounts; wallet sign-in is optional and never required | None |
| D-22 | **Public contact `info@movenrun.xyz`, signed "Team MovenRun"**, on the website and Play listing. Website canonical address `https://movenrun.xyz`; the wallet message domain must match the page a wallet sees, so the site must be served at `movenrun.xyz` (X-21) | Owner decision; wallet domain binding | Owner |
| D-23 | **Free tier only** for v1: Supabase Free (Auth + PostgreSQL) and Render Free (API, `render.yaml`), migrations in the start command. Free plans keep no database backups and the API sleeps when idle | Owner decision: no spend | Owner approves a paid plan |
| D-24 | **No Google Play developer account exists yet (owner, 2026-10-13).** Registration is X-01a–c. **2 Nov 2026 is the engineering and pre-listing target only**: code, tests, ledger, operator guides and listing material ready. No Play availability date is promised, because registration, Google's verification and (for a Personal account) a 14-day closed test and production-access review come after it | Owner fact; a Personal account cannot reach production in under about three weeks from registration | Owner registers an Organization account it truthfully qualifies for |
| D-25 | **Mobile frontend on owner hold (2026-10-13).** No changes to app UI, screens, visuals, navigation or design until the owner sends a new design brief. Work continues on backend, auth, database, infrastructure, privacy, deployment preparation, website functional and compliance files, and tests. A high-severity fix that would need app source stops and is put to the owner first | Owner instruction | Owner's next design brief |
| D-26 | **Reports are uniquely named**: `MOVENRUN_YYYY-MM-DD_MILESTONE_FINAL_REPORT_SHA.md` in `reports/`, where SHA is the short commit of the code the report describes, listed in `reports/INDEX.md`. No report is ever named `FINAL_REPORT.md` again; the earlier shared `FINAL_REPORT.md` is historical | Owner instruction; earlier reports were overwritten in place | None |
| D-27 | **Committed migrations are append-only.** `backend/drizzle/CHECKSUMS.sha256` pins each file's SHA-256 and `migrationChecksums.test.ts` fails on any edit, rename or unlisted file. A fix to an applied migration is always a new migration | drizzle-kit records only which migrations ran, so an edited one would never reach a database that already applied it | None |
| D-28 | **Orphan sweep limits**: each candidate is re-read at Supabase just before deletion, at most 100 deletions per run, one run at a time | Closes the race with a person signing in between listing and deletion; bounds damage from a provider listing error | Change `ORPHAN_SWEEP_MAX_DELETES` |
| D-29 | **Owner hosting decision 2026-10-13: Render Free for the API, the existing Supabase Free project `movenrun` for sign-in and PostgreSQL.** No Render database, no new Supabase project, zero recurring spend, 1,000-account cap kept. Koyeb Free, Google Cloud Run and Oracle Always Free were noted as alternatives and not adopted: Cloud Run needs a billing account, and Oracle carries the operations burden. Render Free is for staging, internal and closed testing, not an uninterrupted public service (`FREE_HOSTING_READINESS.md`) | Owner decision; no spend | Owner approves another host or a paid plan |
| D-30 | **The Blueprint deploys `deploy/render-free-staging`**, a branch moved only to a commit the owner has approved (now `dd8306588667342fab2db0ebd4d55632acadb57a`), never the pre-security release branch. `renderBlueprint.test.ts` guards it | A Blueprint that tracks a moving or outdated branch would deploy unreviewed or insecure code | Owner names another approved commit |
| D-31 | **Background clean-up runs when due, not on a clock**: on each start or wake, after requests, and once a minute while awake. Nothing security-critical depends on it | A sleeping free host cannot run hourly jobs | None |
